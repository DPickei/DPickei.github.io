## Backstory
I hate doing repetitive things manually. Sifting through job listings is very repetitive, so I automated it.

## What it does

User enters typical job preferences like title, salary, location, remote/hybrid/in-person status, etc. The program will return the following:

company | title | minimum salary | maximum salary | location | work life balance rating (glassdoor) | overall_rating (glassdoor) | remote_status | days_since_listed | job_listing_url | years of experience required | recruiter_listing (true/false) | requirements

You can filter for most of the parameters above on almost any job board, but the ones below are collected by few and no one job board concisely aggregates them all.

- **Work life balance rating / overall rating**: Any company I look at I want to get an idea of the impressions from people who already are there. I'm not picky about this, but it's helpful to have an idea, and avoiding having to manually search and login to glassdoor to see this info is very helpful.
- **Years of experience required**: A lot of the time when you're parsing a job description, you might see a role that looks like a fit until you see that the years of experience required are way outside of your own. It's annoying to read through each description just to find this out, so to make it a filter-able option is nice. This was done with NLP (Flash 2.0).
- **Salary**: Though some listings are tagged with a salary, some only list them in their description, so we extract those with NLP.

## What it doesn't do
My goal with this tool is *not* to automate filling out applications. I think that's a zero sum game at best. It's also probably very annoying for people hiring to get a barrage of candidates who are not really a fit.

Instead, the goal is to take the hundreds of listings that are regularly posted, and distill them down into the ones that are right for you. There are tools that do that, AFAIK, [Welcome to the Jungle](https://us.welcometothejungle.com/) is the best version of this out there by a large margin. But there are many small things that I want to add or subtract in my own version that sum to a big difference.

In an ideal world, people looking at listings only see ones relevant to them, and people posting listings only hear from candidates qualified[^fn3].

## 1. Glassdoor Reviews
Any company I see, I'm interested in how people who work there feel. Manually, I'd just do a google search for each company to see their internal ratings. Which is pretty straightforward, automating this was not straightforward. 

#### Initially, the hope is something like this

  1. Company name -->> Glassdoor: Get to company page
  2. Glassdoor ->> Soup object: Fetch page data
  3. Soup object -->> Relevant elements: Parse page data for company ratings
  4. Relevant elements -->> User DB: Append attributes into our db

#### Instead, not a single part of that logic panned out at face value.

  1. ~~Company name -->> Glassdoor: Search company~~
  - The url of a company on glassdoor requires appending the company specific ID (from glassdoor). Take Google for example, their homepage is `https://www.glassdoor.com/Overview/Working-at-Google-EI_IE9079.11,17.htm`. So in order to know the URL for Google, we have to know their ID is 9079.
  - Not to mention, the name of a company on LinkedIn might slightly vary from the name of the same company on Glassdoor, so you couldn't rely on hardcoding a url based on the LinkedIn company name
  2. ~~Glassdoor ->> Soup object: Fetch page data~~
  - Let's say we have that info. Or we use a SERP. Glassdoor uses Cloudflare. Which is annoying. Even once you get to their page, almost all information is blocked unless you have an account.
  3. ~~Soup object -->> Relevant elements: Parse page data for company ratings~~
  - Hard to parse a soup object when we don't have a soup object
  4. ~~Relevant elements -->> User DB: Append attributes into our db~~
  - All hope is lost

#### There are a lot of work arounds, but here's what ended up working for me:

  1. Company name -->> Exposed API endpoint: Get company ID and use it to create a url
    - [Here](https://www.glassdoor.com/api-web/employer/find.htm?autocomplete=true&maxEmployersForAutocomplete=1&term=google) is an example using google
  2. Url -->> 3rd party API: Query API using url as input[^fn4]
  3. 3rd party API -->> Webhook: Get json data
  4. Webhook -->> Local server: Ingest json data
  5. Local server -->> User database: Insert new values

The feeling of this process is kind of like chess, where the answer is typically not from the move you first thought of, the but the one you arrived at after working through all other options.

## 2. Job description parsed using NLP
This was a massive impact. Often when you're reading a description, you're pattern matching certain specifications you're looking for in a role to the job description. This is a perfect use case of AI/NLP in my opinion. At the moment, here's what it collects.

job_listing_id | requirements | yoe_required | roles_counting_towards_yoe | tools_required | tools_preferred | recruiter_listing | salary_min | salary_max

yoe_required (years of experience) is by far my favorite. If you only have 3 yoe, you don't want to see listings with 10. LinkedIn should make this a simple filter, but they don't[^fn5], so I did.

What's great about this is that you can collect whatever you want, and it's easy to implement.

## Challenges in making this

Most code is small snippets like this that move our data along

  # 4) Find which companies we don't already have Glassdoor info on

### So what was challenging?
Flexible architecture--nothing else really compares. The reason is because when this fails, solving anything else goes from `O(n)` to `O(n^x)`, with x being larger the less organized your project is.

Maintainability / extensibility precedes development scalability. If your code is maintainable but not efficient, that's fine, you can improve it later at some point. But if your code is poorly maintained, your development speed will grind down.

It sounds self-evident to emphasize these points, but I think in practice it's hard sometimes to know what aspects you can afford to implement one off solutions and which areas you need to be thoughtful. The answer to this just seems to be you can only know when you've done it before.

But sometimes it's okay to do things that don't scale. Sometimes you just need to know if a path will even work before you lay down a solid foundation. Take our Glassdoor scraping journey as an example. I probably tried over a dozen different implementations before it was working. If I were to try and make perfectly maintainable code every iteration, it'd take much longer to arrive at a solution, assuming I hadn't given up by that point. I'd rather refactor an ugly solution than delete pretty failures.

## Using AI to code
Thinking about maintainability goes hand in hand with thinking about using AI to code. Just as there's technical debt with building a short term solution fast, there's a debt in maintainability when you don't know your code. 

It's a semi-new type of debt by using AI to code. Where you have the answer, but you don't really know what it's doing. So if you need to modify it in any way later on, now you *need* help. But at some point, even AI won't be able to help. So you are forced to pay off the debt, backtrack to where you last knew what was going on, and incrementally catch yourself up.

That being said, here is where AI was hugely helpful:

1. Tedious things to write out that I already know. Especially long sql queries. Let's be honest, we all do it.
2. Getting an idea of my options for solving a problem I'm unfamiliar with.
